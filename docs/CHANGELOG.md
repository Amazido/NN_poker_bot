## 2026-08-08 — Инициализация проекта: модель, логин, движок раундов

**Было:** пустой репозиторий.

**Стало:** заложена архитектура и первая рабочая вертикаль Одесского покера:
- Модель данных и миграция `0001_initial`: `users`, `rules_editions` (редакция
  правил + мета, версионируется), `game_rooms`, `room_players`, `game_rounds`,
  `round_actions` (append-only журнал).
- Логин через Telegram WebApp (проверка initData HMAC-SHA256) + dev-логин (DEBUG),
  JWT, `GET /auth/centrifugo-token`.
- Движок раундов (`poker/engine.py`) как чистый конечный автомат: сдача, вскрытие
  козыря, торги с «крюком», розыгрыш взяток, подсчёт, переход по раундам матча
  (`18 + n`).
- Старшинство карт (`poker/cards.py`) с козырем, двумя джокерами и пустышками.
- Стейт-движок в Redis (источник истины) + публичный/приватный views + публикация
  в Centrifugo (каналы `room:{id}` и `user#{id}`).
- Инфраструктура: Docker Compose (dev/prod), Dockerfile, seed дефолтной редакции.

**Почему:** задача — сделать серверную основу игры под Telegram WebApp с быстрым
обменом событиями по WebSocket; выбран FastAPI + Postgres + Redis + Centrifugo,
переиспользованы проверенные паттерны из референса `TG-game`.

**Зафиксированные решения по правилам (дефолтная редакция `odessa_classic v1`):**
- Некозырной джокер — «второй сверху»: бьёт все обычные карты, но проигрывает
  козырю и козырному джокеру.
- Джокер, ведущий взятку, не задаёт масть сброса (остальные свободны).
- Перебор → фикс `−5`; недобор → `−10` за взятку; точный заказ → `+10 × взятки`;
  заказ 0 и взято 0 → `+10`.
- Игроков 3–5, пик карт всегда 10.

**Допущение (в исходных правилах не описано):** в раунде без козыря старший
джокер — тот, что вскрыт ведущим колоду; второй джокер слабее; оба бьют любые
обычные карты. Может быть изменено отдельной записью.

## 2026-08-08 — Локальный веб-тестер и первый прод-деплой

**Было:** только бэкенд; способа «пощупать» игру и развёрнутого окружения не было.

**Стало:**
- `frontend/index.html` — статический веб-тестер (ваниль, без сборки): несколько
  игроков в одном окне, торги/ходы, обновление поллингом; адрес API вычисляется
  по текущему хосту.
- В `docker-compose.yml` добавлен сервис `frontend` (nginx :3000), `DEBUG` вынесен
  в переменную окружения.
- Прод развёрнут на сервере (Docker Compose): app :8000, frontend :3000,
  postgres/redis/centrifugo. Миграции и сидинг правил — автоматически на старте.

**Почему:** нужно было быстро проверить игру вручную и получить общедоступный
стенд для дальнейшей интеграции с Telegram.

**Смысловые решения по деплою:**
- Centrifugo **не публикуется наружу** (клиенты пока работают по REST-поллингу);
  порт откроем и вынесем ключи из dev-конфига при подключении realtime WS.
- На стенде временно `DEBUG=true` — включён dev-логин, чтобы тестер работал по HTTP
  до подключения HTTPS+домена и полноценного Telegram-входа. Для боевого режима
  переключить на `DEBUG=false`.
- Секреты (`JWT_SECRET`, пароль Postgres) генерируются на сервере в `.env`
  (в репозиторий не попадают); `TELEGRAM_BOT_TOKEN` хранится только в серверном `.env`.

**Заметка по безопасности:** Telegram WebApp требует HTTPS+домен — текущий стенд по
HTTP/IP пригоден для теста бэка и тестера, но не для запуска внутри Telegram.

## 2026-08-09 — Привязка к домену `odessky.win` (HTTPS) и Telegram-вход во фронте

**Было:** стенд доступен только по `http://5.188.21.132:3000` (тестер) и `:8000`
(API); внутри Telegram не запускался; вход — только dev-логин.

**Стало:**
- Приложение доступно по `https://odessky.win`. Цепочка:
  **Cloudflare (TLS на edge) → origin nginx (готовый server-блок FastPanel с
  сертификатом) → наши контейнеры**. Фронт отдаётся статикой из корня сайта, API
  проксируется в `app:8000`.
- Nginx-конфиги добавлены в репозиторий как IaC: `deploy/nginx/odessa_api.conf`
  (общий snippet прокси) и `deploy/nginx/odessky.win.includes` (маршруты
  `/health /ready /openapi.json /auth/ /rooms /docs`). Управляемый FastPanel основной
  конфиг сайта не редактируется — директивы кладутся в штатный include сайта.
- Фронт по домену обращается к API как **same-origin** (без порта); режим `:3000`
  по IP сохранён.
- `frontend/index.html` теперь **Telegram-aware**: при наличии `Telegram.WebApp.initData`
  выполняется вход через `POST /auth/telegram` (один пользователь Telegram = один
  игрок), показывается solo-панель (создать/войти по коду/старт), dev-карточки
  скрываются. В обычном браузере поведение прежнее (мультиигровой dev-тестер).

**Почему:** Telegram WebApp запускается только по HTTPS+домену; домен уже проксируется
Cloudflare на наш сервер, поэтому переиспользуем существующий nginx+сертификат вместо
поднятия своего reverse-proxy (иначе конфликт за порты 80/443 с FastPanel).

**Смысловые решения:**
- TLS терминируется на Cloudflare; между CF и origin — существующий серт сайта
  (режим CF «Full»). Отдельный Let's Encrypt/Caddy не поднимаем.
- Кнопка меню бота (WebApp URL → `https://odessky.win`) настроена вручную в BotFather.
- `DEBUG=true` на стенде пока сохранён (dev-логин как фолбэк для браузерного
  тестирования); отключить (`DEBUG=false`) при переходе в боевой режим.

**Проверка:** `GET https://odessky.win/health` → `{"status":"ok"}`, `/ready` →
`database+redis connected`, `/` отдаёт фронт, `POST /auth/dev` выдаёт токен;
Telegram-вход проверяется открытием WebApp из бота.

## 2026-08-09 — Правило некозырного джокера: «второй сверху» → «только свой цвет»

**Было:** некозырной джокер (цвет ≠ цвету козыря) реализован как «второй сверху» —
бил любые обычные карты любой масти, проигрывая только козырю и козырному джокеру.
Это было зафиксировано как **допущение** (см. запись об инициализации проекта).

**Стало:** некозырной джокер берёт масть сброса **только если её цвет совпадает с
цветом джокера**; против карт чужого цвета он ведёт себя как пустышка (взятку берёт
старшая карта масти сброса). Если некозырной джокер **ведёт** взятку (масть сброса
не задана) — берёт её, но проигрывает любому козырю. Порядок при наличии козыря:
козырный джокер → козыри → некозырной джокер (только свой цвет) → масть сброса →
пустышки.

Пример (козырь `♠`, чёрный): красный джокер `XR` берёт `♥/♦`, но при сбросе `♣`
(чёрная не-козырная) взятку забирает старшая `♣`, а не `XR`.

**Почему:** это дословно соответствует исходным правилам заказчика («тот, который не
совпадает с цветом козыря, берёт только карты своего цвета, но проигрывает козырю»).
Прежняя формулировка «второй сверху» была упрощением и отменяется.

**Технически:** `trick_winner` (`poker/cards.py`) переписан со скалярной модели силы
на явный контекстный порядок приоритетов (правило «свой цвет» не выражается одним
числом — джокер то выше, то ниже масти сброса в зависимости от её цвета). Флаги
`offcolor_beats_oncolor` (некозырной джокер бьёт козырного) и `two_beats_ace_same_suit`
сохранены. Поведение **без козыря** не изменилось (оба джокера бьют обычные, старший —
вскрытый ведущим колоду) — остаётся допущением, может быть пересмотрено отдельно.

**Проверка:** `pytest tests/test_cards.py` (добавлены кейсы: чужой цвет = пустышка,
свой цвет = берёт, джокер ведёт, козырь бьёт ведущего джокера, флаг offcolor) — зелёные.

## 2026-08-09 — E2E по API и рабочий realtime-обмен (Centrifugo)

**Было:** тесты только юнит (карты/правила/движок). Серверная публикация в Centrifugo
была на `start`/`action`, но **не** на `create`/`join`; «труба» наружу закрыта
(порт Centrifugo не проброшен, nginx не проксировал WS); prod использовал dev-конфиг
Centrifugo (namespace `dev`, origin `localhost`, dev-секреты) — под реальный домен и
префикс `prod` подписка бы не работала. Сквозной проверки обмена не было.

**Стало:**
- **E2E по API** (`tests/test_e2e_api.py` + `tests/conftest.py`): приложение
  поднимается поверх реального Postgres (отдельная БД `odessa_test`), live-стейт
  подменяется in-memory, Centrifugo-паблиш — no-op. Покрыто: health/dev-логин,
  лобби (create/join/start, отказ не-создателю), **полный матч** до `match_over`
  на короткой редакции правил, отказ хода не в свою очередь.
- **Realtime достроен**: публикация снапшота лобби добавлена на `create`/`join`
  (`channels.publish_lobby`). Проверка обмена — детерминированно (pytest перехватывает
  публикации на join/start/action) и вживую (`scripts/ws_smoke.py`: подписка по WS +
  публикация через API → получение push).
- **Prod-конфиг Centrifugo** (`backend/centrifugo.prod.json`): namespace `prod` с
  `allow_user_limited_channels`, `allowed_origins: https://odessky.win`, admin off.
  Секреты (`http_api.key`, `client.token.hmac_secret_key`) — из ENV
  (`CENTRIFUGO_API_KEY`, `CENTRIFUGO_TOKEN_SECRET`), в файле их нет.
- **Транспорт наружу**: Centrifugo публикуется только на `127.0.0.1:8001`; nginx
  проксирует `location /connection/` → Centrifugo (IaC: `deploy/nginx/odessa_ws.conf`
  + запись в `odessky.win.includes`). Публичный WS-эндпоинт:
  `wss://odessky.win/connection/websocket`.

**Почему:** нужно было проверяемо гарантировать корректный обмен событиями и иметь
сквозной тест игрового флоу до подключения полноценного фронта на WebSocket.

**Смысловые решения:**
- Секреты Centrifugo не хранятся в конфиг-файле — только в серверном `.env` (env
  перекрывает файл). App и Centrifugo используют одни и те же значения.
- Порт Centrifugo наружу напрямую не открыт (только `127.0.0.1`) — доступ строго
  через nginx/Cloudflare.
- Фронт на `centrifuge-js` в эту итерацию не входит (клиент пока на REST-поллинге).

**Проверка:** `pytest` (35 тестов, вкл. e2e и перехват публикаций) — зелёные;
`scripts/ws_smoke.py` против dev Centrifugo — `OK: received push`.

## 2026-08-25 — Игровой фронт на React, боты и выход из комнаты

**Было:** клиент — статический `frontend/index.html` (ваниль, REST-поллинг,
мультиигровой dev-тестер в одном окне). Realtime существовал только на сервере:
фронт на `centrifuge-js` был отложен «на следующую итерацию». Сесть за стол можно
было только живыми игроками, выйти из комнаты — никак.

**Стало** (влито из ветки `introduce-front`):
- `frontend-app/` — приложение на React 19 + TypeScript (сборка Vite): экраны входа,
  ожидания, торгов, розыгрыша и итогов, стол с раскладкой мест, таймер хода, счёт.
  Обновления — по WebSocket через `centrifuge-js`, с REST-поллингом как фоллбэком.
- Экран выбирается из состояния (`screen-resolver.ts`), причём стол не рисуется,
  пока приватный вид не сойдётся с публичным по `round_index` и `phase` — иначе
  видна новая раздача со старой рукой.
- `POST /rooms/{id}/bots` — хост добавляет бота на свободное место в лобби.
- `POST /rooms/{id}/leave` — выход. В лобби место освобождается и остальные
  сдвигаются; в идущем матче место остаётся за игроком, но помечается `left_seats`
  и доигрывается авто-ходом с коротким дедлайном (`LEFT_SEAT_TIMEOUT_SEC = 2`),
  чтобы не подвешивать остальных на полный `turn_timeout_sec`.
- Публичный вид отдаёт `left_seats` и `turn_deadline` (для таймера и отметки ушедших),
  приватный — `round_index` и `phase` (для сверки с публичным).

**Почему:** нужен был играбельный клиент внутри Telegram вместо отладочного тестера;
боты и выход закрывают практическую проблему «не собралось трёх живых игроков» и
«человек закрыл приложение посреди матча».

**Смысловые решения:**
- Место в идущем матче не освобождается: движок завязан на фиксированное `n_players`,
  пересадка посреди матча не поддерживается.
- Боты — не ИИ, а те же авто-ходы, что и за ушедшего игрока: минимальный допустимый
  заказ и первая легальная карта. Отдельной стратегии у них нет.
- Старый `frontend/index.html` пока остаётся в репозитории как отладочный тестер.

## 2026-08-25 — Личный канал изолирован по комнате; брошенный матч закрывается

**Было:** приватный вид (`{"type":"private"}`) публиковался в личный канал
`{prefix}:user#{user_id}` **всем** местам за столом, включая помеченные `left_seats`,
и **не содержал `room_id`**. Личный канал один на человека и не привязан к комнате,
поэтому клиент не мог отличить, из какой комнаты пришла рука. Матч, из которого все
ушли, продолжал доигрываться авто-ходом (все 18+n раздач) и каждые ~2 секунды слал
приватку бывшим участникам. Клиент при живом WS не опрашивал REST вообще.

**Итог для игрока:** тот, кто уже играл партию и сел за новый стол, залипал на
экране «Загружаем стол…»: приватка из покинутой комнаты перезатирала руку, сверка
`round_index`/`phase` с публичным видом не сходилась, и само это не рассасывалось —
помогала только перезагрузка страницы, и то на несколько секунд. На проде замерено
10 приваток из покинутой комнаты против 1 из актуальной за 20 секунд.

**Стало:**
- Приватный вид несёт `room_id`; клиент отбрасывает приватку с чужим `room_id`.
- Приватка не публикуется на места из `left_seats` — ушедшему рука в покинутой
  комнате не нужна, а его канал уже слушает другая комната.
- Матч, в котором не осталось живых игроков (все ушли, остались боты), закрывается:
  `match_over`, статус `finished`, комната снимается с набора активных.
- Клиент не залипает на рассинхроне: при живом WS работает редкий страховочный
  REST-опрос, а если публичный и приватный виды не сходятся дольше ~1.5 с — пара
  пересобирается запросом `GET /rooms/{id}` + `/hand` (REST отдаёт согласованный
  снимок одной комнаты за раз).
- `subscribeChannel` снимает свой обработчик публикаций и отписывается от канала
  только когда ушёл последний слушатель (раньше обработчики могли накапливаться
  при повторной подписке на тот же канал).

**Почему:** личный канал по своей природе переживает смену комнаты, поэтому
принадлежность к комнате должна быть в самих данных, а не выводиться из того, на что
клиент подписан. Отсюда же и остальное: не слать лишнего, не крутить матч, который
некому играть, и не полагаться на то, что WS-поток всегда полон.

**Смысловые решения:**
- Сверка `round_index`/`phase` из прошлой итерации сохраняется — она защищает от
  смеси новой раздачи со старой рукой. Изменилось лишь то, что рассинхрон больше
  не может стать вечным.
- Возврат в покинутый матч не предусмотрен (место остаётся `LEFT` до конца матча).
- Комната, из которой все ушли **не нажав «Выйти»** (просто закрыли приложение),
  по-прежнему доигрывается авто-ходом: отслеживания присутствия у нас нет. Игрокам
  это больше не мешает — приватка отфильтруется по `room_id`.

**Проверка:** `pytest` (41 тест) — зелёные, из них новые
`tests/test_leave_and_channels.py`: приватка помечена `room_id`, ушедший её не
получает, брошенный матч закрывается (в том числе стол с одними ботами), приватка
новой комнаты помечена новой комнатой. Вживую — `scripts/repro_cross_room.py`
против стенда: `private from room A: 0`. Фронт — `npm run build` (типы + сборка).

## 2026-08-25 — Фиксированная игровая колонка и два бабла

**Было:** весь матч жил в одном «телефоне» 390×780; стол был `flex: 1` и менял
размер, когда снизу появлялись баннер «Твой ход», панель заказа или разное

У оппонентов рисовались рубашки оставшихся карт; заказ выбирался рядом кнопок
0…N.

**Стало:**
- Колонка **360px** (как TG-game). Высота матча складывается из шапки и двух

**Почему:** нужна стабильная раскладка под Telegram fullscreen и десктоп, без
прыжков стола в течение партии.

**Проверка:** `frontend-app` — `npm run build`, `npm run lint`. Вручную —

## 2026-09-24 — Редакция правил как точка расширения: схема, валидация, каталог

**Было:** редакция правил формально существовала (`rules_editions.config`,
JSONB, снапшот в матч при старте), но пользоваться ею было нельзя.

- Блок `deck` в конфиге был **декорацией**: `{"cards": 54, "jokers": 2}` никто
  не читал, `build_deck()` жёстко собирал 52+2, `DECK_SIZE` был константой модуля.
- Валидации конфига **не было вообще**.
- Раздача, не влезающая в колоду, **молча урезалась**: «13 карт на пятерых»
  тихо превращались в 10, то есть игра шла не по тем правилам, что заказали.
- Флаги старшинства (`two_beats_ace_same_suit`, `offcolor_beats_oncolor`) и блок
  `scoring` в движке работали, но наружу выведены не были — ни в API, ни в UI.
- Редакция была одна, выбрать было не из чего, а игрок за столом не мог узнать,
  по каким правилам играет.

**Стало:**
- **Схема конфига v2**: блоки `deck` / `players` / `rounds` / `ranking` /
  `bidding` / `scoring` + `schema_version`. Конфиги v1 поднимаются при чтении
  (`jokers` → `ranking`, `deck.cards` выброшен) — бессрочно, потому что старые
  редакции лежат в БД, а снапшоты идущих матчей в Redis.
- **Валидация** (`RulesEdition.validate()`) при заведении редакции и создании
  стола: неизвестные ключи, диапазон игроков, режим раздач и вместимость колоды
  при любом допустимом числе игроков. В движке **не** вызывается — снапшот
  идущего матча обязан читаться всегда, даже если редакцию признали негодной.
- **Невлезающая раздача — ошибка**, а не повод тихо урезать руку.
- Колода строится по конфигу (`build_deck(jokers)`), число джокеров — 0 или 2.
- `rounds.start` — раздачи могут начинаться не с одной карты (`5..13..5`).
- `bidding.hook` — «крюк» стал переключаемым.
- **Каталог редакций** (`poker/editions.py`), сидится при старте: `odessa_classic`,
  `odessa_circular`, `odessa_blitz`, `odessa_deep`. `GET /rules/editions` отдаёт
  их с человекочитаемым описанием.
- Публичный вид несёт `rules` (`code`, `name`, `summary`); на фронте — выбор
  редакции при создании стола и карточка правил в лобби и в модалке счёта.

**Почему:** дальше по дорожке (см. `BACKLOG.md`) идут бесконечная колода, заказ
вслепую и сезоны с эталонной редакцией. Ни одно из этих правил нельзя выпустить,
пока конфиг остаётся декорацией, а несовместимый набор параметров обнаруживается
падением в середине матча.

**Смысловые решения:**
- Существующие редакции при сидинге **не трогаются**: изменение правил
  выпускается новой версией, иначе поменяется смысл уже сыгранных матчей,
  которые на неё ссылаются.
- Опечатка в ключе конфига — ошибка, а не молчаливое падение в дефолт.
- Имя редакции в конфиге не хранится, поэтому в состояние матча кладётся
  отдельный `rules_meta` (`code`, `name`) — показать игроку, во что он играет.
- Каталог редакций на фронте не критичен: не загрузился — стол создаётся на
  редакции по умолчанию, как было раньше.

**Проверка:** `pytest` — 61 тест (было 41), из них новые на схему и валидацию
(`tests/test_rules.py`) и на редакции по API (`tests/test_rules_editions_api.py`:
каталог, правила стола в лобби и в матче, отказ по неизвестному коду, отказ по
невлезающей раздаче, неизменность правил идущего матча при правке редакции).
Каждая встроенная редакция реально раздаёт свою самую большую руку — проверка
длины последовательности нехватку карт не поймает, а `deal` ловит. Живьём:
приложение на чистой БД засеяло все четыре редакции, `GET /rules/editions`
отдаёт верные описания и длины матчей (9 / 21 / 21 / 19 раздач). Фронт —
`npm run build`, `npm run lint`.

**Прод:** маршруты в `deploy/nginx/odessky.win.includes` перечислены поимённо,
поэтому добавлен `location /rules`. Без выкладки этого файла и перечитывания
nginx каталог редакций через домен работать не будет.

карту, было нечем. С появлением нескольких редакций правил это стало опасно —

**Стало:** логика переехала в `poker/autoplay.py` (`choose_auto_action`) — туда,
где живёт остальное игровое ядро, и тестируется без подъёма приложения.
`tests/test_autoplay.py` (17 тестов): полный матч, сыгранный только авто-ходами,

нуля при выключенном крюке, обязанность масти, обязанность козыря, свобода

правилам; бот молча подвесит раздачу или сломает матч.

- Поведение авто-хода не менялось: ноль, если разрешён, иначе наименьший

- За столом из одних ботов «крюк» **никогда** не срабатывает: все заказывают

  правило не проверяет, и на него есть отдельный тест. Зафиксировано, чтобы
  полнота «матч доигрался» не создавала ложного ощущения покрытия.

## 2026-09-24 — Безлимитная колода и заказ вслепую (этап 2)

**Было:** каркас конфигурации правил существовал, но новых правил в нём не
появилось. Колода всегда была одной физической колодой, поэтому двух одинаковых
карт в раздаче случиться не могло. Заказ всегда делался с открытой рукой:
`private_view` отдавал карты сразу после сдачи, и никакого шага «открыть руку»
не было. Эталонная редакция сезона 1 существовала только как JSON в бэклоге —
сыграть по ней было нельзя.

Отдельно: тай-брейк между одинаковыми картами формально не существовал, но
`trick_winner` фактически отдавал взятку положившему раньше — как побочный
эффект того, что `max()` и `next()` возвращают первый максимум.

**Стало:**
- **`deck.infinite`** — каждая карта тянется независимо из 54 типов, повторы
  возможны и внутри одной руки, и у разных игроков; размер раздачи колодой не
  ограничен (остался только потолок здравого смысла в 52 карты на руку).
- **`ranking.duplicate_first_wins`** — явное правило, кто берёт взятку при
  одинаковых картах; по умолчанию положивший раньше. Применяется одинаково к
  обычным картам, козырям и джокерам.
- **`bidding.blind_allowed`** + **`scoring.blind_bonus`** — торги делятся на два
  шага. Пока игрок не нажал «открыть руку», он не видит собственных карт;
  заказ, сделанный до открытия, считается слепым. Новое действие `open_hand`.
  Надбавка начисляется только при точном заказе, минусы при промахе — в полном
  объёме.
- Раздача несёт `hand_open` и `blind_bids`; приватный вид — `hand_hidden`,
  `hand_count`, `can_open_hand`; публичный — `blind_bids` и `rules.blind_bonus`.
- Во встроенном каталоге две новые редакции: `odessa_infinite` и
  **`odessa_season_1`** — эталон первого сезона (круговое старшинство, заказ
  вслепую +5, недобор −5). Этап 3 получает готовую играбельную редакцию.
- Фронт: на торгах при закрытой руке показываются рубашки, кнопка «Открыть
  руку» и надбавка прямо на кнопке заказа; на столе заказ вслепую помечается.
  В дев-стенде появился экран «Торги втёмную».

**Почему:** заказ вслепую входит в эталонную редакцию сезона 1, поэтому его
нельзя было отложить до этапа 3. Безлимитная колода — первое правило, которое
меняет саму раздачу, а не только подсчёт, и её стоило выпустить до того, как на
редакции начнут ссылаться сезонные результаты.

**Смысловые решения:**
- **«Открыть руку» — не ход.** Очередь и дедлайн не двигаются, открыться можно
  в любой момент торгов, пока сам не заказал. Иначе кнопка превращалась бы в
  бесплатное продление собственного таймера, а открытие соседом — в продление
  таймера тому, кто сейчас думает. Технически: `service.act` теперь двигает
  дедлайн только если очередь реально сменилась.
- **После торгов руки открываются у всех.** «Тёмная» касается только заказа;
  играть вслепую никто не обязан.
- **Авто-ход заказывает вслепую** — пас, а при запрете крюком единицу. Это
  строго выгоднее открытого заказа: слепой заказ не меняет ни значение, ни
  штрафы, только добавляет бонус при попадании. Если игрок успел открыть руку и
  только потом отошёл, вслепую уже поздно — делается обычный заказ. Отдельного
  кода авто-ходу не потребовалось: заказ при закрытой руке и есть слепой заказ.
- **Старые раздачи в Redis доигрываются по-старому.** У снапшотов, начатых до
  этой правки, нет ключей `hand_open`/`blind_bids`; движок читает их через
  `get` и не падает, а не требует миграции живых матчей при деплое.
- **Одинаковые карты — правило, а не случайность.** Прежнее поведение сохранено
  (берёт положивший раньше), но теперь оно задано флагом и закреплено тестами
  на обе стороны: правка `trick_winner` больше не изменит правило молча.

**Проверка:** `pytest` — 118 тестов (было 78). Новое: `tests/test_cards.py`
(повторы в раздаче, раздача крупнее колоды, тай-брейк для обычных карт, козырей
и джокеров в обе стороны, пересечение с «двойка бьёт туза»),

## 2026-09-24 — Стол собирается формой, а не выбирается из списка

**Было:** при создании стола игрок выбирал одну из готовых редакций — список
карточек с названием и описанием. Поменять в редакции что-то одно («хочу как в
сезоне, но короче») было нельзя: либо бери целиком, либо проси новую редакцию в
каталог. Каждое новое сочетание правил требовало выпуска редакции разработчиком,
а карточек становилось всё больше — шесть к моменту правки, и дальше хуже.

Технически стол умел ссылаться только на каталог: `game_rooms.rules_edition_id`
был NOT NULL, своего конфига у комнаты не существовало.

**Стало:** вкладка «Создать» — форма правил. Сверху галочка «Играть по правилам
сезона» (включена по умолчанию): заполняет поля эталоном и блокирует их. Снял —
поля разблокировались, появляется строка быстрых заготовок, и дальше человек
крутит: первая и самая большая раздача, двойка бьёт туза, некозырной джокер
бьёт козырного, разрешить заказ не глядя (с надбавкой), одна колода или
бесконечная, награда за пас, награда за взятку, штрафы за перебор и недобор.
Под формой живая подсказка, сколько раздач выйдет в матче.

- У комнаты появился `rules_config` (JSONB), а `rules_edition_id` стал
  необязательным: заполнено ровно одно из двух (миграция `0002`).
- `POST /rooms` принимает либо `rules_code`, либо `rules` — поля формы.
  Собранный конфиг проходит ту же `validate()`, что и редакции каталога.
- `GET /rules/presets` отдаёт эталон сезона, заготовки и границы полей.
- Проекция «конфиг ↔ поля формы» — `rules.config_from_settings` /
  `settings_from_config`; контракт полей один на вход и на выход
  (`poker/schemas.py`).
- Стол со своими правилами подписан как «Свои правила» (`code` = `custom`).

**Почему:** после этапа 2 правил стало достаточно, чтобы их сочетания были
интереснее готовых наборов, и список карточек начал проигрывать конструктору по
всем статьям сразу: он рос, ничего не объяснял и не давал поменять одну цифру.

**Смысловые решения:**
- **Штрафы вводятся положительным числом** («штраф 5»), знак ставит сервер.
  Минус в поле ввода — лишний повод ошибиться и ввести `-−5`.
- **Заготовка обязана заполнять форму ровно тем, что обещает кнопка.** Форма
  выражает не всё (только `up_plateau_down`, два джокера, посадку 3–5, включённый
  «крюк»), поэтому заготовки отбираются кругом «конфиг → поля → конфиг» со
  сравнением результата, а не списком условий. `odessa_blitz` (без плато) и
  `odessa_deep` (максимум четверо) отсеиваются сами и в форме не показываются,
  оставаясь при этом в каталоге и играбельными по `rules_code`.
- **Потолок раздачи считает бэк** и отдаёт в `limits`: 10 карт при одной колоде,
  20 при безлимитной. Фронт не держит свою копию арифметики колоды, а
  переключение на бесконечную колоду заметно поднимает потолок — это и делает
  правило наглядным.
- **Форма не даёт ввести больше потолка**, но порядок «первая ≤ самая большая»
  на лету не чинит: правка во время набора выдёргивала бы цифру из-под пальцев.
  Вместо этого кнопка блокируется с пояснением.
- **Свой конфиг важнее кода редакции**, если прислали оба: человек его только
  что собрал.
- **Признак сезонного стола — способ создания, а не содержимое.** Стол, собранный
  руками и случайно совпавший с эталоном, сезонным не считается. Это вопрос
  этапа 3, зафиксирован в `BACKLOG.md`.

**Проверка:** `pytest` — 146 тестов (было 118). Новое: `tests/test_table_rules.py`
(знаки штрафов, обнуление надбавки при выключенной галочке, границы формы против
реальной вместимости колоды, круговой прогон каждой встроенной редакции, полный
матч ботами по собранным в форме правилам) и `tests/test_table_rules_api.py`
(заготовки, создание стола формой, правила доезжают до раздачи, приоритет своих
правил, отказы по невлезающей раздаче и по перевёрнутому диапазону). Тесты
проверены на чувствительность: убрал минус у штрафа — упало 4 теста, убрал
проверку кругом — ещё 6 (в заготовки полезли `odessa_blitz` и `odessa_deep`).
Обе подмены откачены. Миграция прогнана вперёд и назад на живой БД. Фронт —
`tsc --noEmit`, `oxlint`, `npm run build`.

**Прод (выкачено 2026-09-24):** перед миграцией снят дамп базы вручную
(`/root/odessa_before_0002.sql`) — автоматических бэкапов на машине нет;

## 2026-09-24 — Зона игрока выше, свой заказ виден в шапке

**Было:** нижний бабл — 216px. За вычетом отступов внутрь помещалось 202px, из
них 86 забирала рука, и на всё остальное оставалось 116px. В торгах втёмную туда
должны были влезть строка «карты закрыты · открыть руку», заголовок, степпер и
кнопка заказа — около 143px. У бабла `overflow: hidden`, поэтому подпись сверху
обрезалась, а карты налезали на кнопку «Заказать втёмную».

Свой заказ и свои взятки нигде не показывались: у соперников под аватаром есть
строка «взял 1/3», а у себя её нет. Строка статуса обрезала лишние плашки
(`flex-wrap: nowrap; overflow: hidden`).

**Стало:**
- `--control-bubble-h` 216px → **281px** (+30%). Содержимое разведено: между
  строками нижнего бабла `gap: 10px`, рука отодвинута от кнопки. Колонка матча
  выросла с 634 до 675px.
- В строку статуса добавлена **своя плашка**: до заказа «заказ —», в торгах
  «заказ 3», в розыгрыше «взял 1 из 3». Зелёная при точном попадании, красная
  при переборе.
- Строка статуса теперь **переносит** плашки, а не обрезает их.

**Почему:** нижняя зона собиралась «в кучу» — это была не теснота на глаз, а
обрезка. Свой результат игрок должен видеть так же, как чужой; под «вы» его
поставить нельзя — своё место стоит у нижнего края бабла, и строка уходит под
обрез. Перенос вместо обрезки: потерять из виду козырь хуже, чем отдать шапке
лишнюю строку.

**Высота бабла одна для обеих фаз** — в розыгрыше остаётся воздух. Это цена за
то, что при переходе «торги → розыгрыш» раскладка не прыгает.

**Проверка:** `tsc --noEmit`, `oxlint`, `npm run build`. Снято скриншотами в
`?mock=1` (Chrome через Playwright, 4 и 5 игроков, экраны «Торги», «Торги
втёмную», «Сброс»): в кадре «как было» подпись обрезана и карты лезут на кнопку,
в кадре «как стало» всё помещается. Четыре плашки статуса умещаются в одну
строку 360px (67 + 92 + 83 + 52px при зазорах 6px).

## 2026-09-24 — Флаг «некозырной джокер бьёт козырного» перестал бить козыри

**Было:** при включённом `ranking.offcolor_beats_oncolor` некозырной джокер
забирал взятку **всегда**, старше любой карты, в том числе козырной, и даже
когда козырного джокера во взятке не было вовсе. На проде в сезонных правилах
(`odessa_season_1`, флаг включён) взятка с выходом в красную карту при чёрном
козыре ушла владельцу `XR`, хотя следом лёг козырь.

**Стало:** флаг переставляет только двух джокеров между собой и срабатывает,
когда оба легли в одну взятку — как «двойка бьёт туза своей масти» требует туза
в том же сбросе. Некозырной джокер без козырного рядом идёт обычным порядком:
берёт масть сброса своего цвета, но проигрывает любому козырю.

**Почему:** названием и описанием флаг всегда обещал «бьёт козырного **джокера**»,
а документированный порядок при козыре — козырный джокер → козыри → некозырной
джокер (свой цвет) → масть сброса → пустышки; флагу положено переставлять первую
строку, а не выносить некозырного джокера над козырями. Версию редакции не
поднимаем: это приведение поведения к уже заявленным правилам, а не новое
правило.

**Формулировка уточнена** в форме создания стола, в `summary()` редакции и в
схеме API: «Некозырной джокер бьёт козырного» → «…бьёт козырного джокера».
Описания встроенных редакций в `editions.py` не тронуты: они сидированы в БД и
оттуда не перезаписываются, менять текст в коде значило бы разойтись с продом.

**Влияние на прод:** снапшот правил идущих матчей лежит в Redis, а логика — в
коде, поэтому после деплоя начатые матчи доигрываются по исправленному
поведению. Уже засчитанные взятки не пересчитываются.

**Проверка:** `pytest tests` (148 зелёных), добавлены два кейса — козырь бьёт
некозырного джокера при включённом флаге (прод-сценарий `QH`, `XR`, `5S` при
козыре ♠) и то же с ведущим джокером. Плюс ручная проверка сценария на проде
после деплоя.
